# Fetch Request Manager (Electron)

Electronでfetchリクエストを実行し、リクエスト内容と結果をセットで管理するアプリの仕様書です。

## 1. 目的

- fetchリクエストをGUIから簡単に実行できるようにする。
- 各リクエストの結果(成功/失敗、レスポンス、実行時間)を1件単位で追跡できるようにする。
- 実行履歴を見返しやすくし、どのリクエストが遅かったかをすぐ確認できるようにする。

## 2. 対象ユーザー

- APIの疎通確認を行う開発者
- HTTPリクエストの試験を繰り返し行うQA/検証担当

## 3. 画面仕様

画面は大きく2エリアで構成する。

1. fetchコマンド入力エリア(最上部)
2. 実行結果一覧エリア(入力欄の下)

### 3.1 fetchコマンド入力エリア(最上部)

- 画面の一番上に常時表示する。
- 入力項目:
	- コマンド入力欄(複数行テキスト)
	- クリップボード監視ON/OFFトグル
	- キュー自動処理ON/OFFトグル
- 実行方法: Enterキー押下で実行
- 想定入力例:

```bash
fetch('https://api.example.com/users', {
	method: 'GET',
	headers: { 'Content-Type': 'application/json' }
})
```

- コマンド入力後、Enterキー押下でリクエストを開始する。

### 3.1.1 クリップボード監視モード

- 画面上部にクリップボード監視のON/OFFトグルを配置する。
- 監視モードがONの場合、クリップボードの文字列を定期的に監視する。
- クリップボードの内容がfetchコマンドと判定された場合、自動でfetchコマンドを実行する。
- 同じクリップボード内容は連続実行しない。
- 自動実行時は入力欄に対象コマンドを反映したうえで実行し、実行後に入力欄をクリアする。
- fetch実行中もクリップボード監視は継続する。
- 実行中に新しいfetchコマンドを検知した場合は、実行結果一覧に「実行前」カードとして追加する。
- 「実行前」カードは現在の実行完了後に自動実行され、同じカード上で状態が更新される。
- アプリ再起動時に「実行前」カードが残っている場合は、カード情報からキューを再生成する。
- クリップボード監視をOFFにした場合でも、既にキュー済みの「実行前」カードは削除しない。
- キュー済みの「実行前」カードの処理は、クリップボード監視のON/OFFに関係なく継続する。
- クリップボード監視のON/OFFは、新規にクリップボードを監視してキューへ追加するかどうかのみを制御する。
- キュー自動処理のON/OFFは、キュー済みカードを自動で実行するかどうかを制御する。
- キュー自動処理がOFFの場合、実行前カードは保持されるが自動実行されない。
- キュー自動処理をONへ戻すと、保持していた実行前カードの処理を再開する。
- クリップボード監視ON/OFFとキュー自動処理ON/OFFの状態はローカルに保存され、リロード後も維持される。

### 3.2 実行結果一覧エリア(入力欄の下)

- リクエスト実行後の履歴をカードまたはテーブルで表示する。
- 表示順は「実行開始時間の降順」とする。
	- 新しく開始したリクエストほど上に表示する。
- 各行(各カード)に表示する項目:
	- 実行開始日時
	- リクエスト概要(URL、method)
	- 実行時間(ms)
	- 実行ステータス(実行前/実行中/成功/失敗)
	- 詳細表示ボタン
	- 再実行ボタン
	- 削除ボタン

- 再実行ボタン押下時は、対象カードのリクエスト内容を使って新規実行を行う。
- 再実行結果は別レコードとして追加し、一覧の先頭側に再配置される(実行開始時間の降順)。
- 削除ボタン押下時は、対象カード(対象レコード)のみ一覧から削除する。

## 4. 実行ステータス表示仕様

### 4.1 実行中

- リクエスト送信からレスポンス確定まで、対象行に「実行中」を表示する。
- 視認性向上のため、ローディングインジケータを併記する。

### 4.2 実行完了(成功)

- HTTP通信が正常完了した場合、対象行に「成功」を表示する。
- 併せてHTTPステータスコード(例: 200)を表示する。

### 4.3 実行完了(失敗)

- fetch例外、タイムアウト、HTTPエラーなど失敗時は「失敗」を表示する。
- 取得可能なエラー情報(message、statusなど)を保持する。

## 5. レスポンス確認仕様(リクエストごと)

- 実行結果一覧の各行から「詳細表示」で個別結果を確認できる。
- 詳細表示には少なくとも以下を含める:
	- リクエスト内容(実行したfetchコマンド)
	- レスポンスヘッダ
	- レスポンスボディ
	- 実行時間
	- 実行ステータス(成功/失敗)
- これにより、実行後のレスポンスをリクエスト単位で追跡できる。

## 6. データ保持仕様

- 1リクエスト実行ごとに、以下のデータを1レコードとして保持する。
- レコードはローカルDB(IndexedDB)に永続化する。
- 保持件数は最大30件とし、31件目以降は実行開始時間の古いレコードから削除する。

```ts
type RequestRecord = {
	id: string;
	startedAt: string; // ISO8601
	command: string; // 入力されたfetchコマンド
	url?: string;
	method?: string;
	durationMs: number;
	status: 'running' | 'success' | 'failure';
	httpStatus?: number;
	responseHeaders?: Record<string, string>;
	responseBody?: string;
	errorMessage?: string;
};
```

- 一覧表示時は `startedAt` の降順でソートする。

## 7. 基本フロー

1. ユーザーが最上部入力欄にfetchコマンドを入力する。
2. Enterキー押下でリクエスト開始。
3. 一覧に新規レコードを追加し、ステータスを「実行中」で表示。
4. 完了後、実行時間を確定して「成功」または「失敗」に更新。
5. 一覧は実行開始時間の降順で表示(新規開始が先頭)。
6. ユーザーは任意のレコードから詳細を開いてレスポンスを確認。
7. ユーザーは任意のレコードの再実行ボタンから同一条件で再実行できる。
8. ユーザーは任意のレコードの削除ボタンで対象行のみ削除できる。

### 7.1 クリップボード監視時のフロー

1. ユーザーがクリップボード監視をONにする。
2. クリップボード文字列を定期監視する。
3. 新しいクリップボード内容がfetchコマンドと判定された場合、自動で実行する。
4. 一覧に新規レコードを追加し、通常の手動実行と同じルールで結果を管理する。
5. 生成済みの「実行前」カードは監視ON/OFFに関係なく順次処理される。
